## 测试1：缓存 vs DB 性能对比

| Cache 平均延迟 | 0.54 ms |
| DB P99 延迟 | 7.77 ms |
| Cache P99 延迟 | 0.76 ms |
| 平均加速比 | 2.3x |
| 冷启动加速比 | 10.2x |

|---------|-------------|----------------|--------|------|

| 2 | 0.71 | 0.60 | 1.2x | 缓存命中 |

| 4 | 0.54 | 0.54 | 1.0x | 性能接近 |

**图1：缓存 vs DB 延迟对比（10个商铺）**

> 图表说明：柱状图，对比 10 个商铺（Shop 1 - Shop 10）的 DB 延迟与 Cache 延迟。横轴为商铺 ID，纵轴为延迟（ms），包含"DB 延迟"和"Cache 延迟"两组柱状数据。其中 Shop 1 的 DB 延迟最高（7.77ms），Cache 延迟为 0.76ms，差距最为明显；Shop 2 - Shop 10 的 DB 延迟与 Cache 延迟均接近（0.47 - 0.71ms），差异较小。

> **分析**
>
> 冷启动时 DB 延迟高达 7.77ms（连接池初始化 + SQL 解析 + 结果映射），缓存仅 0.76ms，加速 10.2 倍。后续查询 DB 延迟降至 0.5ms 左右（连接复用），与缓存差距缩小。在高并发场景下 DB 连接池会成为瓶颈，缓存能有效减少 DB 压力。

## 测试5：一人一单分布式锁验证

同一用户并发发起 10 次秒杀请求，验证 Redis Lua 脚本中的 SISMEMBER 判断 + Redisson 分布式锁能否防止重复下单。

| 指标 | 值 |
|------|-----|
| 并发请求数 | 10 |
| 成功下单 | 1 |
| 被拒绝 | 9 |
| 一人一单 | PASS |
| 平均延迟 | 3.09 ms |
| P99 延迟 | 5.11 ms |

> **结论**
>
> 10 次并发请求仅 1 次成功，DB 中仅 1 条订单记录。Lua 脚本的 SISMEMBER 判断在 Redis 层即拦截了 9 次重复请求，无需进入数据库。P99 仅 5.11ms，说明 Lua 脚本执行效率极高。

## 优化建议

### 1. 缓存层优化

> **现状：** 缓存命中时 P99 为 0.76ms，DB 查询 P99 为 7.77ms（冷启动）。本地环境下 DB 也很快（0.5ms），加速比不明显。
>
> **建议：** 生产环境下 DB 延迟会显著增加（网络 + 负载），缓存加速比可达 10-50 倍。可引入多级缓存（Caffeine 本地缓存 + Redis）进一步降低延迟。

### 2. 并发查询优化

> **现状：** 100 并发下 P99 为 21.74ms，QPS 3,306。长尾延迟主要来自 GC 和线程调度。
>
> **建议：** 调优 JVM GC 参数（G1 -> ZGC），增加 Tomcat 线程池（默认 200 -> 500）。对于读多写少的场景，可引入读写分离。

### 3. 秒杀优化

> **现状：** 30 并发秒杀 P99 为 31.67ms，QPS 803。Lua 脚本执行 + MQ 发送是主要耗时。
>
> **建议：** 使用 Redis Cluster 分片提升 Lua 执行吞吐；MQ 发送改用异步确认模式（publisher confirm）减少阻塞；增加秒杀库存预热点（避免冷启动）。

### 4. 限流优化

> **现状：** 验证码接口 QPS=1，限流率 90%。Guava RateLimiter 为单机限流。
>
> **建议：** 分布式部署时需引入分布式限流（Redis + Lua 或 Sentinel）。验证码接口建议增加 IP 维度限流 + 手机号维度限流（60 秒内同一号码只能发 1 次）。

### 5. 连接池调优

> **当前配置：** HikariCP 默认最大 10 连接，Redis Lettuce 连接池默认配置。
>
> **建议：** 生产环境 HikariCP 调至 maximum-pool-size=20-50，Redis 连接池 max-active=50。根据压测结果动态调整，避免连接池耗尽导致请求排队。
