# 点评项目秒杀接口 1000 并发压测报告

**Seckill Stress Test Report — 1000 Concurrency**

基于 Redis Lua + MQ 异步架构的秒杀接口高并发压测验证

> 本报告替代 2026-08-02 旧版（30 并发，秒杀 QPS 803）。本轮将并发提升至 1,000，并完成了三轮瓶颈优化与 C 客户端交叉验证。

- 测试时间: **2026-08-20 10:37 - 10:47**
- 环境: **localhost / Spring Boot 8081 / macOS**
- 数据量: **1,000 测试用户 / 秒杀券 ID=105 / 初始库存 500**
- 工具: **Python 3 + asyncio + httpx（连接预热）/ Apache Bench（C 客户端交叉验证）**

## 测试概述

本次压测覆盖四个递进场景：限流保护验证（场景A）、无限流真实吞吐三轮优化（场景 B1 → B2 → B3）、C 客户端基线交叉验证。每个场景压测后执行 Redis-DB 全量对账。

| 指标 | 值 |
|------|-----|
| 最大并发 | 1,000 |
| 秒杀接口真实吞吐（ab 验证） | **6,579 QPS** |
| 真实吞吐 P99（ab 验证） | **282 ms** |
| 超卖检查 | PASS（所有场景零超卖） |
| 一人一单 | PASS（1,000 用户零重复下单） |
| Redis-DB 一致性 | PASS（库存/订单数双向一致） |
| 异步落库收敛 | 500 单 ≈ 4s |

## 测试方法

压测脚本 `stress_1000.py` 四阶段流程：

1. **prepare**：重置 DB 库存（500）与订单表，清理 Redis 库存键、订单 Set、Stream 与 pending 队列
2. **inject**：从 DB 取 1,000 个用户，直接写 Redis Hash 会话（绕过登录接口 QPS=5 限流），TTL 10h
3. **run**：asyncio + httpx，先预热建立 1,000 条 keep-alive 连接，再用 `asyncio.Event` 门闸让 1,000 协程同一瞬间放行
4. **verify**：轮询 DB 订单数直至收敛（连续 3 秒不变），对账库存 / 订单数 / 买家去重数 / Redis 一致性

响应分类：`ok`（下单成功）/ `limited`（限流拒绝）/ `soldout`（库存不足）/ `dup`（重复下单）/ `error`。

## 场景A：限流保护验证（@RateLimit qps=50）

1,000 用户瞬时并发秒杀，Controller 层 Guava RateLimiter 令牌桶（50 QPS）生效时的系统行为。

| 指标 | 值 |
|------|-----|
| 总请求 | 1,000 |
| 成功下单 | 110 |
| 被限流拒绝 | 890 |
| 限流拦截率 | 89.0% |
| 实际放行速率 | ≈46 QPS（110 单 / 2.38s） |
| 墙钟时间 | 2.377 s |
| QPS（含拒绝） | 420.7 |
| 平均延迟 | 1,251.94 ms |
| P99 | 2,263.75 ms * |

\* 场景A本轮尚未引入连接预热，延迟含 1,000 条 TCP 建连的 SYN 积压开销；限流拒绝本身是毫秒级返回（见场景B3 对比）。

**对账结果（verify A）**：

| 检查项 | 值 | 结果 |
|--------|-----|------|
| 初始库存 → 剩余库存 | 500 → 390（DB 与 Redis 一致） | PASS |
| 售出 = DB 订单数 | 110 = 110 | PASS |
| 买家去重数 | 110（无重复下单） | PASS |
| Redis 订单 Set 基数 | 110（与 DB 订单数一致） | PASS |

> **结论**
>
> 限流器精确放行 110 个请求（2.38s 窗口 × 50 QPS ≈ 119 个令牌，尾部请求未抢到令牌），其余 890 个在入口即被拒绝，后端 Redis / MySQL 仅承受约 46 QPS 的真实压力。限流作为第一道防线把 1,000 并发的冲击削减了 89%，验证了"入口最早拦截"的设计意图。

## 基线交叉验证：Apache Bench（C 客户端）

Python 客户端测得的 903 QPS 存在压测端自身瓶颈（asyncio 事件循环 + GIL）。用 C 实现的 Apache Bench 交叉验证服务端真实能力：

```bash
ab -n 3000 -c 1000 -k \
   -p /tmp/empty_post.txt -T "application/json" \
   -H "authorization: $TOKEN" \
   http://127.0.0.1:8081/voucher-order/seckill/105
```

| 指标 | 值 |
|------|-----|
| 请求 / 并发 | 3,000 / 1,000 |
| Requests per second | **6,579** |
| P99 | **282 ms** |

> 说明：测试时库存已售罄，3,000 个请求绝大多数走 Lua 脚本"库存不足"快速拒绝路径。该路径与成功路径同样经过会话读取 + 限流检查 + Lua 执行的完整 Redis 往返，因此该数字反映秒杀接口完整请求链路的吞吐上限。

> **结论**
>
> 服务端真实吞吐 ≥ 6,579 QPS，是 Python 客户端测量值（903）的 7.3 倍。B3 的 903 QPS 是压测客户端瓶颈，不是服务端瓶颈。

## 瓶颈分析（三轮优化的定位过程）

### 1. macOS TCP SYN 积压（贡献最大）

- **现象**：B1 / B2 的 P50 高达 2.3-2.8s，远超业务逻辑耗时
- **定位**：macOS `kern.ipc.somaxconn=128`，1,000 个瞬时 SYN 超出 accept 队列，触发 SYN 重传指数退避（1s / 2s / 4s）
- **修复**：压测前预热 1,000 条 keep-alive 连接，正式压测零建连开销 → P99 从 4.2s 降到 1.0s
- **生产启示**：连接池 + keep-alive 是高并发客户端的必备配置；Linux 生产环境同样需要关注 `somaxconn` 与 `tcp_max_syn_backlog`

### 2. HikariCP 连接池（次要）

- **现象**：B2 调大连接池后 QPS +19.5%
- **定位**：默认 `maximum-pool-size=10`，异步消费者批量落库 500 单时与其他 DB 操作竞争连接
- **生产启示**：连接池大小需压测确定，经验公式 `connections = core_count * 2 + spindle_count` 只是起点

### 3. 压测客户端自身（最终瓶颈）

- **现象**：B3 优化到位后 Python asyncio 客户端只能打出 903 QPS
- **定位**：换 ab（C 实现）后同一接口打到 6,579 QPS
- **启示**：压测结论必须先排除压测端瓶颈，否则会严重低估服务端能力（本例差 7.3 倍）
